# 线性化提交整理

## 概述

把开发分支或 worktree 的历史整理成一串**按意图组织的线性提交**。先从实际改动确定每条提交要完成的事，再决定它包含的改动、提交顺序和说明。整理本身就是完整交付。用户同时要求合并时，再以 `--ff-only` 方式并入目标分支（未指定时默认为主干）。

常见两种场景：
- **整理并合并**：整理完历史后，线性合入目标分支（用户指定或默认主干）。
- **纯整理**：只重写本分支历史，不合并——包括整理某个指定 commit 之后的历史，或整理已推送的个人独占分支（整理后按用户确认执行 `--force-with-lease`）。

为什么要做提交整理：主干历史是团队理解演进、二分排错（`git bisect`）和**线上异常时按单条提交精准回退**的依据。粒度合理的直接标准是——任何一条提交出问题时，单独 `git revert` 它就能安全回退，不会牵连无关改动。

## 四条不可妥协的原则

1. **先核对提交归属。** 默认整理用户自己的提交。合并他人提交须有明确授权，并保留原作者归属（详见「保留作者归属」）。
2. **不跳 git hooks**：任何提交都禁止使用 `--no-verify` 绕过项目的 pre-commit / commit-msg 检查；hook 报错就修原因，不绕过。
3. **保持最终文件树一致**。在授权范围内重组已有改动，整理后的文件树（tree）必须与整理前完全一致。
4. **当前会话亲自执行与校验**：盘点、分组、重写历史和 diff 验证全部在当前会话直接完成，不外包给子代理。历史整理依赖对全部 diff、hook 行为、冲突上下文和作者归属的连续把握，拆分委派容易引发上下文断层和静默偏差。

## 前置检查

1. **确认工作区干净**：运行 `git status`；有未提交改动时请用户先处理，不要擅自 `git stash`。
2. **确认候选范围和实际下界（`base`）。**
   - 用户指定 commit hash 时，以该 hash 作为候选下界。
   - 用户未指定 hash 时，使用 `git merge-base HEAD <目标分支>`。目标分支以用户指定为准，未指定时默认主干（通过 `git symbolic-ref refs/remotes/origin/HEAD` 或 `main` / `master` / `trunk` 判断，不确定就询问用户）。
   - 用下一节的 `git log` 查看候选范围内的原提交 `author`，与用户已确认的 Git 作者身份核对。默认从 `HEAD` 往前只整理连续属于用户的提交。保留他人或归属不明的提交及其原 hash。
   - 在线性历史中，候选范围内有需保留的提交时，以最后一条为实际 `base`，并在方案中说明范围调整。重写它之前的提交也会改变它的 hash。用户已明确授权重写指定提交时，按授权确定范围。
3. **确认操作对象**：明确是在当前分支还是指定 worktree/分支操作。跨 worktree 时先跑 `git worktree list` 定位，在目标 worktree 目录操作或切换至对应分支，避免改错分支。
4. **创建备份分支并告知用户**：执行 `git branch backup/<分支名>-pre-linearize <当前HEAD>`（重名时加日期后缀）。验证一致通过后再清理，失败时随时用于恢复。
5. **已推送分支单独确认**：若分支已推送到远端，重写后需要 force-push。必须先确认该分支为本人独占（无人基于它继续开发），并得到用户对 force-push 的明确同意；推送时只允许 `git push --force-with-lease`，严禁裸 `--force`。多人共享分支禁止重写，直接说明原因并停止。

## 工作流程

### 1. 盘点真实改动

```bash
git log --reverse --format='%h %an <%ae> %s' <base>..HEAD
git show --stat --patch <commit>
git diff <base> HEAD
```

逐条查看实际 diff，记录各块改动的用途和作者，再对照分支的最终差异核实后续修补落在哪里。原提交标题和正文作为查找背景的线索。

### 2. 设计分组方案并请用户确认

在确认的范围内按「粒度判断准则」归组。只有用户明确允许合并的他人或归属不明的提交，才可与其他提交合成一条。仅获重放授权的提交逐条保留。按改动依赖排好目标顺序，再为每组拟定提交信息。

```text
候选历史（用户的作者身份为 Alice）
  0a1b2c3 docs     记录登录接口约定 [Author: Bob，保留为 base]
  a1b2c3d wip      实现登录和列表分页
  b2c3d4e tweak    修补登录失效处理
  c3d4e5f fix      补齐列表分页空态
  d4e5f6a test     补登录失效用例

整理后（保留 0a1b2c3，其后的 4 条整理成 2 条）
  feat(auth): 支持登录及会话失效处理 [Author: Alice]
    a1b2c3d 中 auth/ 的改动 + b2c3d4e + d4e5f6a
  feat(users): 支持用户列表分页 [Author: Alice]
    a1b2c3d 中 users/ 的改动 + c3d4e5f
```

重写前展示目标提交的顺序、说明、改动来源、作者和 `Co-authored-by` 安排。拆分时标出涉及的文件或改动块。方案经用户确认后执行。

### 3. 执行历史重写

按确认好的意图分组选择 Git 操作。

- **整条原提交刚好符合分组时**，用 `git rebase -i <base>` 按计划调整顺序、合并或改写说明。用 `GIT_SEQUENCE_EDITOR` 设置操作顺序，需改写说明时用 `GIT_EDITOR` 提供拟定的信息。
- **需要拆开原提交重新归组时**，用 `git reset --mixed <base>` 把暂存区重置到 `base`，保留工作区的最终内容。用 `git add -- <路径>` 暂存整个文件，用 `git add -p -- <路径>` 挑选改动块。拆分新文件时先用 `git add -N -- <路径>`，让它出现在 diff 中。每条提交前用 `git diff --cached` 核对暂存内容与分组是否一致，再用拟定的信息提交。

Windows 下为 `GIT_SEQUENCE_EDITOR` 和 `GIT_EDITOR` 使用非交互脚本。遇到冲突时先检查相关 diff，再按目标提交的意图处理。

**严禁使用 `--no-verify`**：如果项目 hook 失败，先修复原因再提交；若是整理前旧历史本身就通不过现行 hook（例如中途升级过 lint 规则），如实向用户说明，由用户决定如何处理，绝不擅自跳过。

### 保留作者归属

- `rebase` / `squash` 时保留原作者。合并时核对每组首条提交的作者是否与方案中的主作者一致。
- 获明确授权合并不同作者的提交时，取主体改动的作者作为 author，其余作者在提交正文末尾追加 `Co-authored-by: 名字 <邮箱>`。主作者无法确定时，在分组方案中一并确认。重写时保留对应改动原有的 `Co-authored-by`。
- 重新提交时用 `--author="原名字 <原邮箱>"` 恢复原作者，必要时用 `--date` 保留原时间。

### 4. 一致性验证（不可跳过）

用 `git log --reverse <base>..HEAD` 和逐条 `git show` 核对目标顺序、提交说明与每条提交的实际范围。确认排除在重写范围外的提交仍以原 hash 保留在分支历史中，再验证最终文件树。

```bash
git diff <备份分支> HEAD       # 输出必须为空
git diff --stat <备份分支> HEAD # 确认文件级零差异
```

接着运行项目的最小必要验证（如类型检查或受影响测试），确认整理前后功能等价。

- **验证通过后删除备份分支**：`git branch -D backup/<分支名>-pre-linearize`，避免在分支列表残留噪音；最终汇报时仍附上原 `HEAD` 的 commit hash（可在 reflog 中追溯）。
- **若 `git diff` 非空**：立即用 `git reset --hard <备份分支>` 恢复并排查原因，此时绝不能删备份分支。

### 5. 并入目标分支（可选，仅在用户明确要求时）

```bash
git rebase <目标分支>
git checkout <目标分支> && git merge --ff-only <branch>
```

使用 `--ff-only` 确保不产生 merge commit。**用户只要求「整理」时到第 4 步即止**，不擅自合并或推送。用户要求同步远端已推送分支时，确认前置检查第 5 条后再执行 `git push --force-with-lease`。

## 粒度判断准则

**一条提交 = 一个可独立理解、可独立 `git revert` 的完整意图。**

- **合并同一意图的改动。** 围绕同一个功能、问题或重构目标的实现、后续修补、漏改文件和配套测试一起提交。符合这一条件的改动可以跨越不相邻的原提交、多个文件或模块。
- **拆开独立意图。** 把可以单独交付和回退的改动分开，例如功能实现与独立重构。原提交混有多个意图时，按文件或同一文件内的改动块拆开。`wip`、`checkpoint` 里的改动也逐块归组。
- **检查回退范围。** 每条提交应能用一句话讲清目的。单独 `git revert` 时，一起撤回的改动应都服务于这个目的。

## 提交信息格式

按分组后的实际 diff 写清每条提交要实现什么、修复什么或解决什么问题。原信息含糊或与最终范围不符时，直接重写，即使这条提交无需合并或拆分。原信息已经准确时可以沿用，正文保留仍适用的背景和约束。

默认格式如下。

```text
type(scope): 中文描述
```

- **type**：`feat` / `fix` / `refactor` / `perf` / `docs` / `test` / `chore` / `build` / `ci` / `style`
- **scope**：小写英文模块名（取自目录或功能模块，如 `auth`、`api`、`table`、`build`）。每条只取最核心的一个 scope，不堆砌多个；全局改动可用 `repo`、`deps`
- **描述**：中文，动词开头（增加 / 支持 / 修复 / 移除 / 抽取 / 统一……），说清**做了什么**而非实现细节；结尾不加句号；不超过 50 字

示例：

```text
feat(auth): 支持刷新令牌自动续期与失效登出
fix(table): 修复筛选条件重置后未回到第一页的问题
refactor(api): 统一错误码拦截与国际化回退逻辑
test(orders): 补充订单取消与并发扣减库存用例
chore(ci): 拆分类型检查与单元测试流水线步骤
```

> 如果目标项目已有明确的提交格式约定（以主干近期提交历史或项目规范为准），**项目约定优先于上述默认格式**。

## 安全红线

- 已推送分支在 force-push 前必须确认独占并获用户明确同意，且仅用 `--force-with-lease`。
- 验证通过前备份分支必须一直保留；确认代码零差异后再按流程删除。
- 只重写 `base` 之后的本分支提交，严禁触碰已合入主干的公共历史。
- 严禁 `--no-verify`；严禁覆盖原作者信息。
- 重写与校验在当前会话亲自完成，不委派子代理。
- 用户未要求合并或推送时，整理并验证完成后即停。
