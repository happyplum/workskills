# 深度思考模式

## 概述

日常交互默认保持简洁、直接推进任务；只有用户明确触发深度思考时，才展开更充分的分析。

深度思考追求的是**有证据支撑、覆盖关键边界的结论**，而不是漫无边际的发散，也不是把「我先想 A、再想 B」的内心独白倒给用户。

## 强制规则

| # | 规则 | 检查标准 |
|---|---|---|
| 1 | **展开但紧扣当前任务**：所有分析必须直接服务于用户的具体问题和目标，不展开无关的背景科普或泛泛建议 | 每段内容都与当前决策或产出直接相关 |
| 2 | **结论必须有证据或显式假设支撑**：禁止凭直觉、泛泛经验或未经核查的猜测直接下结论 | 核心判断都能对应到代码、文档、实测结果或明确写出的假设 |
| 3 | **补齐权衡、边界与失败路径**：不只给单一路径的乐观推论，主动列出主要取舍、临界条件和出错时的表现 | 关键方案包含取舍对比及风险/失败路径 |
| 4 | **按任务相关性选择分析维度**：默认覆盖技术实现正确性，按需要补充性能、兼容性、可维护性或扩展性，不强行凑齐所有维度 | 只展开对当前问题真正有影响的维度 |
| 5 | **输出结论与依据，不复述思维过程**：直接呈现结构化判断和证据，不写「我首先考虑…接着想到…」式的思考流水账 | 无冗余的逐步内心独白 |

## 推荐输出结构

按当前问题按需选用，跳过不适用的部分：

1. **依据与权衡**：已查证的事实（附文件、行号或测试依据）、明确假设以及主要方案的取舍。
2. **风险与边界**：容易出错的临界条件、失败路径及对应预防措施。
3. **结论 / 产物**：明确建议、行动方案或具体代码改动。

## 反例

| 看似合理但错误 | 正确做法 |
|---|---|
| 「这种设计应该没问题，行业常见做法都是这样。」（无依据拍脑袋） | 列出查证到的代码/文档事实与前提假设，再下结论 |
| 「我先考虑了 A，后来觉得 B 也不错，仔细想想还是 C 更好……」（复述思考过程） | 直接给出方案对比表、核心取舍依据与推荐结论 |
| 用户只想定位一个并发 bug，却从操作系统的历史和哲学讲起（无边界发散） | 聚焦并发竞态路径、触发条件、复现证据与修复方案 |
