# OMO 计划审查协议

本 skill 是计划审查流程的**单一协议源**：审查模式、循环规则、reviewer 委托注入模板、收敛与成本门槛均在此定义。审查的格式与判定标准以 `omo-plan-structure` 为准（官方四类、verdict 格式、判定附件格式），本文件不复制。

## 审查模式

- **单审**：只执行 Momus 阶段。
- **双审**：两阶段各自循环——先 Oracle 循环，再 Momus 循环。

## 两阶段循环

1. **Oracle 阶段**：发送 Oracle 审查委托（注入模板见下）→ `[REJECT]` → Prometheus 修订计划 → Oracle 重审 → 循环至 `OKAY`。
2. **Momus 阶段**：Oracle `OKAY` 后发送 Momus 审查委托 → `[REJECT]` → Prometheus 修订 → Momus 重审 → 循环至 `OKAY`。
3. Momus 阶段的修订在 Momus 循环内消化，**不回送 Oracle**；最终通过 = Oracle `OKAY` 在先、Momus `OKAY` 在后。
4. **温链复审**：修订后续用原 reviewer 会话只核闭合与 diff 新矛盾（不可续用时构造审查胶囊注入新会话）；默认 1 轮、最多 2 轮，超限停止循环升级用户裁决。

## Oracle 委托注入模板

发给 Oracle 的审查委托必须附带以下判据（判据随委托注入，不改 Oracle 自身提示词）：

- 只阻断**架构层大雷**——执行期无法自救且测试无法拦截级：必炸路径、生命周期竞态、契约自相矛盾、生产接线缺失、目标级方向错误。
- 显微级发现以 `handoff-to-momus` 非阻断建议随 verdict 移交，不作为 `[REJECT]` 理由。
- 架构确认以送审版本的完整计划为对象。

## Momus 委托注入模板

发给 Momus 的审查委托必须附带：

- **机械维度穷举要求**（逐维标注「已核对无发现 / 发现 N 条」）：类型签名与字段类型跨节一致性、数值单位与字段名映射、调用方与消费方核对、文件归属与并发矩阵/写域一致性、路由标注明确性、验收命令可执行性与覆盖面、契约-AC 一致性与区块结构规范。
- **执行判定要求**：按 `omo-plan-structure` 的判定附件格式，对每个实施 task 输出 `tdd` / `split` / `route` 三类判定，附于 verdict 之后。

## 收敛与成本

- 审查墙钟估算 > 执行墙钟估算 50% 时，须 `WHY_HIGH_REVIEW_COST` 点名该轮审查对执行的价值；否则降级审查 lane（Oracle 架构预检降 Momus 单审、温链复审降 diff-only）；成本问题只降 lane、不加轮。
- 复审只核对既有范围和有证据的 blocker；已解决且无新证据的不重提。
- 三类执行判定随初审执行；温链复审仅对 diff 新引入的 task 补判定，不重做全量。
- Oracle 不承担通用代码质量、QA 或「为了完整再看一遍」；Momus 只针对计划缺陷与可执行性给出修订方向，不得改变产品方向——方向变更只能来自用户。
