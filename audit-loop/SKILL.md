# 审计循环（Audit Loop）

## 概述

通过「只读审查 → 疑似问题二次确认 → 修复与验证 → 原审查会话温链复审」的闭环推进质量收敛，直到核心循环审查子代理明确确认无未决问题（`PASS`）；随后由用户决定是否再用干净代理复核一轮。

核心设计有四点：
- **审修分离**：审查子代理只读不改文件，修复由当前会话（或其派发的执行侧）完成。
- **温链复审**：每轮修复后继续在**同一审查者的原会话**中追加本轮修复增量与验证结果，不换审查者、不重建会话。审查者保留前序上下文，不会把已闭合的问题反复翻案，也能重点排查修复本身是否引入新回归。
- **证据确认**：审查发现的疑似问题先由轻量级只读子代理核对证据，只有确认成立的问题才向用户汇报并进入修复。
- **有界收敛**：修复必须先过本地定向验证再送复审，遇到分歧或范围持续膨胀时及时停止并交由用户裁决。

> **与 `lzy-review-work` 的分工**：`lzy-review-work` 用于按改动风险决定单轮审查要覆盖哪些维度；本 skill 用于把审查出的问题通过「修 → 复审」闭环收敛到无误。

## 审查者与对象确认

进入循环前，先明确「谁来审」和「审什么」：

| 用户输入情况 | 处理方式 |
|---|---|
| 已指定审查子代理（如「用某只读评审代理做审计循环」） | 直接使用该子代理，进入第 1 轮审查 |
| 未指定审查子代理（如只说「走审计循环」） | 先从最近对话推断候选（例如上一轮审查用过谁、刚讨论过哪个审查代理），用一句简短问题确认「是否用 X」；无法推断时，列出当前环境可用的只读审查型子代理请用户选择 |
| 指定的是负责写代码、构建或执行任务的子代理 | 拒绝并请用户改选——审查者必须保持只读，不能让执行者审查自己产出的修改 |

补充规则：
- **不写死代理名单**：按角色性质判断——只读分析/评审型代理合格，承担文件修改或任务执行的代理不合格。如果当前环境没有用户点名的代理，如实说明并请用户改选，不要擅自替换。
- **合并确认**：如果审查对象（提交区间、文件/目录、实现代码或设计方案）也不明确，与确认审查者合并为一个问题一次问清，不要连环追问。

## 循环流程

每轮按「审查 → 问题确认 → 修复 → 温链复审」推进；未通过则继续下一轮，所有复审都回到原审查会话。

### 阶段 1：审查

启动一个新的只读审查子代理，清晰提供以下信息：
- **审查范围**：精确的提交区间（如 `git log A..B`）、文件列表或文档路径；
- **上下文与已有验证**：本轮改动目标以及已跑过的测试/类型检查结果（避免审查者重复跑耗时构建）；
- **只读约束**：明确禁止修改文件、禁止变更 git 状态、禁止运行耗时构建；
- **输出格式**：逐条列出发现的问题，附 `file:line` 证据、严重级别（阻断 / 非阻断）和最小修复建议；
- **通过标准**：无疑似问题即返回 `PASS`；发现的问题先视为疑似问题，不直接向用户汇报。

### 阶段 2：问题二次确认

- 将审查者给出的每条疑似问题及证据交给轻量级只读确认子代理；独立问题可并行确认。至少传递：
  - 审查者的原问题描述，不先入为主地改写结论；
  - 声称的 `file:line`、相关引文、复现步骤或命令输出；
  - 审查范围与改动目标，供确认者自行定位核对；
  - 只读约束：禁止修改文件、禁止变更 git 状态、禁止运行耗时构建。
- 确认子代理只核对指定问题，不做完整审查、不提供修复方案。每条问题必须返回：
  - 判定：`CONFIRMED`（证据支持问题成立）或 `REJECTED`（证据不足或问题不成立）；
  - 自己实际核到的 `file:line`、引文或只读检查输出，而不是转述审查者；
  - 一句话判定理由。
- 只有 `CONFIRMED` 问题才向用户汇报并进入修复；`REJECTED` 问题不汇报、不修复，保留判定与证据供原审查者复核。
- 本轮没有确认成立的问题时，将确认结果与证据送回原审查会话复核；当前会话不能自行把原审查结果改成 `PASS`。

### 阶段 3：修复

- 只修复已确认问题，按正常开发方式由当前会话或执行侧修改，保持与审查者、确认者分离。
- 每轮修复必须先通过定向验证（受影响的测试、类型检查或 diff 核对）；涉及 git 仓库时，建议按独立意图原子提交，便于复审直接引用 commit hash。
- 已确认的非阻断项（如测试补充、合理改进建议）默认一并修复；如果明确决定不修，必须在复审说明中如实列出并给理由，由审查者判断是否接受，禁止静默跳过。

### 阶段 4：温链复审与裁定

向**同一审查者的原活动会话**发送续审消息，只包含本轮增量：
- 上轮已确认问题清单，以及对应的修复提交（commit hash）或具体变更摘要；
- 被驳回问题的确认结果与证据，供审查者复核原判断；
- 修复后的定向验证结果；
- 要求审查者逐项给出判定：`FIX-CORRECT`（已修妥）、`FIX-INCOMPLETE`（修复不完整）或 `FIX-INTRODUCES-REGRESSION`（修复引入新问题），并检查修复是否带出其他回归。无需重发首轮背景。

裁定分支：
- 审查者明确 `PASS` 且已确认问题全部闭合 → **核心循环 PASS**，进入下方的用户决策，不直接输出终态报告。
- 仍有未决问题或新发现 → 将本轮问题及证据交阶段 2 二次确认，确认成立的问题再回到阶段 3 修复。

## 核心 PASS 后的可选干净复核

核心循环 PASS 后，先询问用户：「是否使用一个干净的新子代理再做一轮只读审查复核？」

- **用户拒绝**：直接整理终态报告，不擅自启动新审查。
- **用户同意**：启动一个无前序审查与修复对话上下文的新只读子代理，只提供审查范围、改动目标、只读约束与输出格式。干净代理只审查一轮，不修复文件，也不替代原审查者。
- 干净代理发现的疑似问题同样先经阶段 2 二次确认：
  - 无疑似问题或疑似问题均未确认成立 → 干净复核通过，整理终态报告；
  - 有确认成立的问题 → 只汇报这些问题，回到阶段 3 修复，并在修复后送原审查会话温链复审。再次核心 PASS 后，重新由用户决定收尾或再做一轮干净复核。

## 安全边界与熔断条件

- **不随意重开主审查会话**：核心循环内的复审必须复用同一审查者的原会话，避免丢失上下文或推翻已确认的结论。仅当原会话因故障不可恢复时才允许新建，且新建时必须补全前几轮所有发现与修复记录；核心 PASS 后的干净复核按用户选择单独新建，不替代主审查会话。
- **确认子代理保持轻量只读**：只核对指定问题及证据，不做完整审查、不直接修复，也不代替审查者给出最终 `PASS`。
- **禁止通过削弱验证换取通过**：不得删测试、放松断言或掩盖报错来制造 `PASS`。
- **先验证再复审**：未经定向验证的修改不得送去复审。
- **轮数熔断**：同一问题连续 2 轮修不好，或连续 3 轮不断冒出全新问题（范围蔓延），立即停止循环，把分歧点和现状摊开交由用户决策，不无限空转；干净复核确认的新问题也计入熔断。
- **审查者全程只读**：任何一轮都禁止审查子代理、确认子代理或干净复核代理直接改代码。

## 终态报告

结束时向用户提供简明汇总，至少包括：
- 总审查轮数及是否进行了干净复核；
- 每轮二次确认成立的问题数量及「问题 → 修复提交/改动」对应关系；
- 最终 `PASS` 依据（原审查者核心结论摘录与已确认问题闭合情况）；
- 用户选择过干净复核时，附该轮审查与确认结论；
- 如有经审查者同意保留的非阻断项，附明理由。

## 反例

| 看似合理但错误 | 正确做法 |
|---|---|
| 每轮复审都新开一个审查子代理 | 在同一审查者的原会话追加本轮增量，保持温链复审 |
| 审查者报出问题就直接汇报或修复 | 先把问题与证据交轻量只读子代理确认，只汇报并修复确认成立的问题 |
| 让确认子代理顺手全面审查或改代码 | 只核对指定问题的证据，保持轻量、只读 |
| 核心循环 PASS 后直接结束 | 先询问用户是否需要干净代理复核 |
| 干净代理发现确认问题后直接改完交付 | 回到修复与原审查会话温链复审，直至再次核心 PASS |
| 让负责改代码的子代理兼任审查者 | 严格审修分离，只选用只读审查型子代理 |
| 悄悄跳过非阻断建议不提 | 决定不修时在复审说明中明示并给理由 |
| 同一分歧卡了 4 轮还在来回改 | 连续 2 轮未解即熔断，交给用户拍板 |
