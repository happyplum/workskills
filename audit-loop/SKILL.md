# 审计循环（Audit Loop）

## 概述

通过「只读审查 → 修复与验证 → 同一审查会话增量复审」的闭环推进质量收敛，直到审查子代理明确确认无未决问题（`PASS`）。

核心设计有三点：
- **审修分离**：审查子代理只读不改文件，修复由当前会话（或其派发的执行侧）完成。
- **同会话增量复审**：每轮修复后继续复用**同一个审查会话**，只提交本轮修复增量与验证结果。审查者保留前序上下文，不会把已闭合的问题反复翻案，也能重点排查修复本身是否引入新回归。
- **有界收敛**：修复必须先过本地定向验证再送复审，遇到分歧或范围持续膨胀时及时停止并交由用户裁决。

> **与 `lzy-review-work` 的分工**：`lzy-review-work` 用于按改动风险决定单轮审查要覆盖哪些维度；本 skill 用于把审查出的问题通过「修 → 复审」闭环收敛到无误。

## 审查者与对象确认

进入循环前，先明确「谁来审」和「审什么」：

| 用户输入情况 | 处理方式 |
|---|---|
| 已指定审查子代理（如「用某只读评审代理做审计循环」） | 直接使用该子代理，进入第 1 轮审查 |
| 未指定审查子代理（如只说「走审计循环」） | 先从最近对话推断候选（例如上一轮审查用过谁、刚讨论过哪个审查代理），用一句简短问题确认「是否用 X」；无法推断时，列出当前环境可用的只读审查型子代理请用户选择 |
| 指定的是负责写代码、构建或执行任务的子代理 | 拒绝并请用户改选——审查者必须保持只读，不能让执行者审查自己产出的修改 |

补充规则：
- **不写死代理名单**：按角色性质判断——只读分析/评审型代理合格，承担文件修改或任务执行的代理不合格。如果当前环境没有用户点名的代理，如实说明并请用户改选，不要擅自替换。
- **合并确认**：如果审查对象（提交区间、文件/目录、实现代码或设计方案）也不明确，与确认审查者合并为一个问题一次问清，不要连环追问。

## 循环流程

每轮包含三个阶段；未通过则返回阶段 2 进入下一轮。

### 阶段 1：审查

- **首轮审查**：启动一个新的只读审查子代理，清晰提供以下信息：
  - **审查范围**：精确的提交区间（如 `git log A..B`）、文件列表或文档路径；
  - **上下文与已有验证**：本轮改动目标以及已跑过的测试/类型检查结果（避免审查者重复跑耗时构建）；
  - **只读约束**：明确禁止修改文件、禁止变更 git 状态、禁止运行耗时构建；
  - **输出格式**：逐条列出发现的问题，附 `file:line` 证据、严重级别（阻断 / 非阻断）和最小修复建议；
  - **通过标准**：零未决问题即返回 `PASS`。
- **后续复审（复用原审查会话）**：向**同一个审查会话**发送续审消息，只包含本轮增量：
  - 上轮问题清单；
  - 对应的修复提交（commit hash）或具体变更摘要；
  - 修复后的定向验证结果；
  - 要求审查者逐项给出判定：`FIX-CORRECT`（已修妥）、`FIX-INCOMPLETE`（修复不完整）或 `FIX-INTRODUCES-REGRESSION`（修复引入新问题），并检查修复是否带出其他回归。无需重发首轮背景。

### 阶段 2：修复

- 收到审查结果后，逐项完成修复（按正常开发方式由当前会话或执行侧修改，保持与审查者分离）。
- 每轮修复必须先通过定向验证（受影响的测试、类型检查或 diff 核对）；涉及 git 仓库时，建议按独立意图原子提交，便于复审直接引用 commit hash。
- 非阻断项（如测试补充、合理改进建议）默认一并修复；如果明确决定不修，必须在复审说明中如实列出并给理由，由审查者判断是否接受，禁止静默跳过。

### 阶段 3：裁定

- 审查者确认无未决问题且明确 `PASS` → **审计循环完成**，整理终态报告反馈给用户。
- 仍有未决问题（包括 `FIX-INCOMPLETE`、`FIX-INTRODUCES-REGRESSION` 或新发现）→ 回到阶段 2 继续下一轮。

## 安全边界与熔断条件

- **不随意重开审查会话**：复审必须复用原审查会话，避免丢失上下文或推翻已确认的结论。仅当原会话因故障不可恢复时才允许新建，且新建时必须补全前几轮所有发现与修复记录。
- **禁止通过削弱验证换取通过**：不得删测试、放松断言或掩盖报错来制造 `PASS`。
- **先验证再复审**：未经定向验证的修改不得送去复审。
- **轮数熔断**：同一问题连续 2 轮修不好，或连续 3 轮不断冒出全新问题（范围蔓延），立即停止循环，把分歧点和现状摊开交由用户决策，不无限空转。
- **审查者全程只读**：任何一轮都禁止审查子代理直接改代码。

## 终态报告

结束时向用户提供简明汇总，至少包括：
- 总审查轮数；
- 每轮发现数量及「问题 → 修复提交/改动」对应关系；
- 最终 `PASS` 依据（审查者核心结论摘录）；
- 如有经审查者同意保留的非阻断项，附明理由。

## 反例

| 看似合理但错误 | 正确做法 |
|---|---|
| 每轮复审都新开一个审查子代理 | 复用同一个审查会话，只传本轮修复增量 |
| 让负责改代码的子代理兼任审查者 | 严格审修分离，只选用只读审查型子代理 |
| 悄悄跳过非阻断建议不提 | 决定不修时在复审说明中明示并给理由 |
| 同一分歧卡了 4 轮还在来回改 | 连续 2 轮未解即熔断，交给用户拍板 |
