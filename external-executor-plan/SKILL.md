# 外部执行方案生成

## 概述

将需求、已确认决策和可验证现状整理成外部执行者可以独立使用的方案。读者没有当前聊天上下文，也不默认拥有当前工具、模型或代理体系。

交付物重点是：为什么做、做到什么程度、明确怎么做、保持什么、替代什么、如何验收。方案应在影响正确性、业务语义和对外契约的决策上闭合；局部命名及不改变语义的编码细节留给实现者。

本 skill 的交付范围仅为方案，不启动方案中的产品实现、迁移、部署或外部派发。用户另行要求执行时，按该请求和目标环境规则处理。

## 核心规则

1. **主目标不漂移**：先明确用户要解决的问题和成功标准，再组织配套工作。不能让迁移、目录调整、工具接线等配套事项取代核心交付。
2. **脱离聊天可读**：将会影响实现的已确认结论写进正文；不用“按前述”“沿用上版”“参考我们的讨论”代替契约。证据链接补充正文，不代替关键要求。
3. **证据与目标分开**：区分已验证现状、用户已确认目标、低影响实现默认和待确认事项。不能把目标写成现状，把推测写成事实，或把拟运行测试写成已通过。
4. **保留约束，控制扩围**：需求、例外、明确不做项和行为保持条件须可追溯。未经确认的业务默认、兼容支持、重试、回退和新功能不得混入必做项；选定方案后不要把关键选择留给执行者重选。
5. **执行器中立**：默认不输出 GPT 等模型型号、effort、代理角色、派发命令、并发额度、工具专属账本或当前会话的 todo。保留真实的工程依赖、资源约束和验收门。用户明确指定执行器格式时，仅适配其已核实的必需契约，不自动套用本地编排体系。
6. **完整修订**：完善已有方案时输出完整替代稿，合并新增决定并保留仍有效细节；不能仅追加章节、用摘要替代旧契约，或让正文与附录互相冲突。用户明确只要差异或摘要时按其要求交付，并标明它不是独立完整方案。

## 工作流程

### 1. 收集最小充分依据

先读取用户提供的需求、上一版方案及可访问的相关讨论，提取主目标、已接受选择、否决方向、硬约束和未决问题。已有答案不重复询问。

涉及代码仓库时，确认工作区、分支、revision 和相关未提交差异，按当前工作区规则读取项目规范、架构 skill 及相应产品文档，再定点核对入口、调用方、状态 owner、公共接口和测试命令。不要为生成方案做无关全仓审计。

无法访问代码或外部资料时说明证据边界；不能编造路径、符号、版本或当前行为。资料不足但不阻碍独立部分时先推进独立部分。

保留可交接的定位信息：仓库或工作区身份、代码基线、关键文件相对路径与符号、文档章节或正式来源。必要时标注目标环境绝对路径；不把本机私有路径当成其他执行器必然可访问的依赖。机密只写获取边界和变量名，不写值。

### 2. 闭合会改变实现的决策

能通过检查发现的事实先查证。只有答案会改变业务结果、对外契约、授权范围、架构归属或不可逆行为时才向用户澄清；说明具体选项及影响，不问可以从仓库得到的问题。

重大未决项尚未解决时，交付明确标为草案的内容及阻塞问题，不宣称“可直接执行”。不得用默认假设替用户决定权限、排序、金额、状态流转或失败后的业务结果。

对不改变业务含义的局部实现选择，沿用已验证惯例并直接确定。适用环境要求架构咨询时按其规则完成，不将咨询过程或模型分工复制进交付方案。

### 3. 形成目标设计

按行为或子系统组织，给出一个已选方案。只有取舍会影响后续维护时，简述选定理由及被放弃路径，不倾倒所有探索过程。

下列内容按实际涉及情况补齐，不机械制造无关章节：

| 涉及对象 | 需要写清的设计内容 |
|---|---|
| 模块或共享实现 | 职责、依赖方向、输入输出、权威状态源、真实调用链及旧实现退出 |
| 公共接口或数据模型 | 变化及保持条件、生产者与消费者、归一化边界、必要字段语义和错误结果 |
| 请求、事务或异步流程 | 阶段和结果、合法转移与回边、资源生命周期、取消及迟到结果；仅在已采用该设计时明确状态机，不强制所有任务引入状态机 |
| 重试或并发 | 原有规则与本次变化、决策 owner、计数及资源作用域、执行时点和可观测验收；不凭重构新增策略 |
| 迁移或持久化 | 源与目标、字段保持与转换、提交边界、恢复方向、冲突处理及旧源退出条件 |
| UI 或公共组件 | 用户可见行为、公共组件复用、状态/主题/尺寸、契约与预览同步 |
| 协议或外部依赖 | 已核实版本和依据、支持范围、转换或拒绝条件、鉴权及敏感数据边界 |

共享或替代设计同时列出退出对象。只统一接口、保留多套同语义执行体，不视为完成共享；确需跨阶段保留过渡层时，写明 owner、退出条件及验收点。

保留会决定行为的细节，包括字段、能力矩阵、端口、错误状态、排序、重试窗口、释放时点、兼容范围和例外；无具体依据或与任务无关的细节不补造。示例不能偷渡新规则。

### 4. 组织实施与验收

按可独立验证的交付单元安排顺序，标明真实依赖、交付结果和验收条件。涉及同一权威源或共享实现的切换要闭合，不能拆出长期并行真相或半迁移可运行状态。

验收条目描述可观察结果，而非“检查没问题”：对照目标、原行为保持、具体错误/边界路径，以及必要的迁移和恢复场景。共享重构还要验证调用方接入和旧实现退出，不能只测最终输出。

测试、类型检查、构建和 smoke 命令来自已核实脚本或文档；缺少可运行入口时标为待准备并写清前置条件，不编造命令。说明验证范围和未覆盖边界，区分本地模拟与真实服务验证，不默认授权付费、生产或破坏性操作。

### 5. 完整修订与交付

以最新有效方案为底稿，将每项新决定融入对应正文，同时修正受影响接口、实施顺序、退出清单及验收。核对旧要求的去向：保留、明确替代或经确认删除，不静默省略。

输出前进行一次离开聊天上下文的检查：执行者能否确定目标、边界、关键选择、数据及状态归属、实施依赖和验收结果；能否辨认现状与目标；是否存在相互冲突的重复规则。

默认直接给出中文 Markdown 完整方案。用户要求保存或指定文件时写入相应位置；未要求落盘时不擅自修改仓库文件。遵循宿主要求的计划展示格式，不把宿主包装标记当成外部执行器的通用语法。

复杂度决定篇幅：简单任务可用“目标与边界／关键变更／实施与验收”三节；复杂任务可展开“依据与现状／目标设计／接口与数据／迁移及旧源退出／实施依赖／验收”。保持决策细节，不为凑模板添加章节，也不为简短删掉有效约束。

## 交付前核对

- 主目标、成功标准、明确变化和保持条件相互一致，配套事项没有抢占主目标。
- 无依赖聊天才能理解的关键结论；证据基线、关键入口及必要依据可定位。
- 重大决策已闭合；未验证内容和未执行检查如实标识，无伪造完成状态。
- 公共契约、调用方、状态 owner、失败路径和退出对象覆盖本次真实影响面。
- 修订稿完整替代旧稿；无遗漏、冲突、无意扩围或已否决方案复活。
- 实施顺序和验收能约束结果，交付物不混入当前执行器的治理噪声。

## 反例

| 看似合理但错误 | 应采用的方式 |
|---|---|
| “按上轮讨论统一请求链，其他不变” | 写出执行职责、保持条件、重试边界及旧执行体退出，便于无上下文交接 |
| 用户要独立模块，直接规划独立部署服务 | 先核实独立性的含义，锁定模块、进程和部署边界 |
| “采用状态机”后让每个节点自行重试或跳转 | 若状态机已被采用，明确唯一编排 owner、阶段结果和合法回边 |
| 为了通用，把某项目的状态机、数据库或迁移策略套给所有计划 | 提炼决策检查方法，具体架构来自当前项目证据和已确认目标 |
| 新版仅追加补丁，省略旧版接口和授权规则 | 输出融合后的完整稿；明确请求差异稿时才只输出差异 |
| 将模型档位、代理名字和并发槽位写入工程方案 | 保留交付依赖和工程资源限制，具体执行分工交给目标执行器 |
