# 外部执行方案生成

## 概述

将需求、已确认的决策和仓库中可核实的现状，整理成一份**独立完整、可直接交接**的实施方案。假设读者看不到当前聊天记录，也不使用当前会话的特定 AI 工具、模型或代理编排体系。

方案重点说清六件事：**为什么做、做到什么程度、具体怎么做、保留什么、替换/删除什么、如何验收**。所有会影响正确性、业务含义和对外接口的决定必须在方案中写定；不影响语义的局部命名和编码细节留给实现者。

> **范围边界**：本 skill 只交付方案文档，不直接开始改代码、做迁移、部署或派发执行任务。如果用户另外要求实施，再按对应请求处理。

## 核心规则

1. **主目标不偏移**：先写清用户要解决的问题和成功标准，再安排配套改动。不要让目录整理、脚手架调整或迁移铺垫喧宾夺主。
2. **脱离聊天也能读懂**：所有影响实现的已确认结论必须直接写进正文，禁止用「按前面讨论」「沿用上一版」「如前所述」代替具体要求。链接只作补充，不能替代关键规则。
3. **区分现状、目标与待确认**：明确分开「已核实的现状」「已确认的目标」「低影响默认项」和「待用户确认的事项」。不能把目标写成现状，把猜测写成事实，或把计划跑的测试写成已通过。
4. **守住约束，不擅自加戏**：需求、例外情况、明确不做项和必须保持的行为都要可追溯。未经确认的新功能、兼容兜底、重试机制或回退策略不得偷偷塞进必做项；已经选定的方案也不要再留给执行者重新做选择。
5. **与执行工具解耦**：不写入当前会话使用的模型名称、推理档位、代理角色名、并发配额、工具专属账本或内部 todo。保留真实的工程依赖、资源限制和验收门槛即可。只有用户明确指定目标执行器格式时，才按其核实过的必需格式适配。
6. **修订时输出完整替代稿**：完善旧方案时，把新决定融进对应章节，输出一份可直接替代旧稿的完整方案，确保正文与旧规则没有矛盾。只有用户明确只要「差异清单」或「摘要」时才只给增量，并注明它不是独立完整方案。

## 工作流程

### 1. 收集最小必要依据

先阅读用户提供的需求、旧版方案和相关讨论，提炼主目标、已定方案、否决方向、硬约束与未决问题。已有明确答案的不重复追问。

涉及代码仓库时，确认工作区、分支、当前 commit 和未提交改动，按仓库既有规范和文档，定点核查入口文件、调用方、数据/状态归属、公共接口和验证命令，避免为了写方案去做无关的全仓通读。

无法访问代码或外部资料时，如实说明信息边界，不编造文件路径、符号名、版本号或当前行为；不影响独立部分推进的，先完成可确定部分。

保留可供交接的定位信息：仓库标识、代码基线、关键文件相对路径与核心符号、正式文档出处。不要把本机私有绝对路径当成外部执行者必然可访问的依赖。敏感信息只写环境变量名和获取方式，绝不写具体值。

### 2. 收口会影响实现的关键决策

能查代码或文档确认的事实直接查证。只有答案会改变**业务结果、对外接口、权限边界、架构归属或不可逆操作**时，才向用户提问；提问时列出选项和各自影响，不问仓库里能直接查到的问题。

如果存在尚未拍板的重大未决项，交付物必须明确标注为「草案」并置顶阻塞问题，不能宣称「可直接执行」。严禁擅自替用户默认权限、排序、金额、状态流转或失败后的业务处理方式。

不改变业务语义的局部技术细节，沿用项目既有惯例直接确定即可。

### 3. 编写目标设计

按业务功能或子系统组织正文，只给出一个已选定的方案。仅当取舍会影响后续维护时，简明写清选择理由与放弃的备选方案，不倾倒整个探索过程。

按实际涉及范围补齐以下设计细节，不涉及的不用硬凑章节：

| 涉及范围 | 需要写清的内容 |
|---|---|
| 模块或共享逻辑 | 职责边界、依赖方向、输入输出、核心状态归属、调用链以及旧实现如何退场 |
| 公共接口或数据模型 | 变更点与保持兼容的范围、上下游调用方、字段转换规则、关键字段含义与错误返回 |
| 请求、事务或异步流程 | 关键阶段与结果、状态流转和合法回退路径、资源创建与释放时机、取消或迟到响应的处理（仅在确实使用状态机时写明状态机，不强行引入） |
| 重试或并发控制 | 原有策略与本次调整、由哪一层负责决策、重试次数/资源作用域、触发时机与可观测验证点（不因重构凭空新增策略） |
| 数据迁移或持久化 | 来源与目标、字段保留与映射规则、提交边界、回滚方式、冲突处理及旧数据源下线条件 |
| UI 或公共组件 | 用户可见行为、复用哪些公共组件、状态/主题/尺寸要求以及组件接口同步 |
| 外部协议或第三方依赖 | 已核实的版本与依据、支持范围、格式转换或拒绝条件、鉴权与敏感数据边界 |

涉及共享抽取或替换旧实现时，必须明确写出**旧实现何时、如何删除**。只包了一层统一接口却长期保留两套相同逻辑的，不算完成重构；如果确实需要过渡期，写明负责人、下线条件和对应验收点。

凡是会影响实际行为的具体细节（字段名、端口、错误码、排序、超时、兼容例外等）都要写实；无依据或无关的细节不要编造，也不要在示例里暗藏正文没写的新规则。

### 4. 组织实施步骤与验收标准

按可独立验证的交付步骤排序，标明真实前后依赖、每步产出和验收条件。涉及同一核心数据源或共享实现的切换应当形成闭环，避免留下长期并存的两套数据源或半迁移状态。

验收条目必须描述**可观察的结果**，而不是「检查没问题」：覆盖主目标达成、原有行为未破坏、具体错误与边界场景，以及必要的迁移/回滚验证。共享重构还需核对所有调用方已接入且旧代码已移除。

测试、类型检查、构建和冒烟命令必须来自仓库里核实过的脚本或文档；若当前缺少运行入口，标明「待准备」和前置条件，不编造命令。说明验证覆盖面与未覆盖部分，区分本地模拟和真实环境验证，不默认授权付费、生产或破坏性操作。

### 5. 整合修订与交付

基于最新有效稿整合修订，把每项新增决定落回对应章节，并同步更新受影响的接口、步骤顺序、旧实现清理清单与验收标准。逐一核对旧版要求：保留、明确替代还是经确认删除，不悄悄漏掉。

交付前按「脱离聊天能否直接照做」检查一遍：执行者能否看清目标、边界、关键选择、数据归属、步骤依赖和验收结果；能否分辨现状和目标；全文有没有前后矛盾的条款。

默认直接输出中文 Markdown 完整方案；仅在用户要求保存时写入指定文件。篇幅随复杂度伸缩：简单任务用「目标与边界 / 关键变更 / 实施与验收」即可；复杂任务可展开「现状与依据 / 目标设计 / 接口与数据 / 迁移与旧实现退出 / 实施顺序 / 验收」。

## 交付前核对

- 主目标、成功标准、变更项和保持不变的约束前后一致，配套工作未抢占主目标。
- 没有必须看聊天记录才能看懂的表述；仓库基线、入口路径和关键依据均可定位。
- 关键业务决策已确定；未验证项与待确认项如实标出，未伪造测试通过。
- 公共接口、调用方、状态归属、错误路径和旧实现退场覆盖了实际影响面。
- 修订稿完整替代旧稿，没有遗漏约束、前后打架或已否决方案复活。
- 实施步骤和验收条件清晰可执行，未混入当前聊天工具的内部代理或模型信息。

## 反例

| 看似合理但错误 | 正确做法 |
|---|---|
| 「按刚才聊的统一请求封装，其他保持不变」 | 写清封装职责、兼容边界、错误处理规则和旧封装删除范围，保证无上下文也能执行 |
| 用户说「拆成独立模块」，直接设计成独立部署的微服务 | 先确认「独立」是指代码模块、独立包还是独立进程/服务，再定边界 |
| 在某类重构方案里强行套用状态机或复杂重试框架 | 方案结构由当前项目证据和需求决定，不凭惯性硬套过度设计 |
| 修改方案时只输出「本次新增的 3 条补充」，省略旧接口和约束 | 输出合并后的完整替代稿；只有用户明确只要差异时才给增量 |
| 把「用某模型跑」「派 2 个子代理并行」写进工程方案 | 只写工程任务依赖和资源约束，具体怎么派发交给目标执行器 |
