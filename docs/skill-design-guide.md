# Skill 设计与维护指南

> **维护任何 skill 前，先读本指南。** 本指南是本仓库编写与重构 skill 的统一规范，综合了主流 Agent Skills 渐进式披露实践与本仓实际维护经验。

## 核心原则：渐进式披露（Progressive Disclosure）

Skill 不应一次性倾倒全部细节，而应分层按需加载：

| 层 | 位置 | 大小建议 | 加载时机 | 写什么 |
|---|---|---|---|---|
| **L0 触发** | frontmatter `description` | ~50–100 tokens | 会话开始全量注入 | 「什么时候用 + 触发词」，**纯触发条件** |
| **L1 规范** | `SKILL.md` 正文 | **<500 行**（红线） | 触发匹配时加载 | 概述、核心规则、工作流/决策表、反例 |
| **L2 详情** | `references/*.md` | 按需 | 正文**显式指示**阅读时才加载 | 领域细节、按场景查阅的子规范 |
| **L3 执行** | `scripts/*`、`assets/*` | 不限 | 执行时不进 context，仅输出消耗 token | 确定性脚本、模板、数据 |

**加载机制要点**：
- `description` 是唯一常驻 context 的字段，本质是**触发器**。
- `references/` 必须由正文明确给出阅读时机（如「决定文件放哪时，读取 `references/placement.md`」）；含糊的「参考相关规范」通常不会触发读取。
- 引用保持**一层深**：`SKILL.md` → `references/*.md`，不要 reference 嵌套 reference。

## `description` 写法

> **Description = 什么时候用（When to Use），不是这个 skill 怎么干活（How It Works）。**
> 在 `description` 里堆砌工作流摘要时，模型容易跳过正文直接按描述自由发挥。

- **正确（纯触发条件）**：
  - 「当确认运行环境为 Windows + PowerShell，且需要启动或管理后台长运行进程、等待端口就绪或按 RunId 停止残留时使用。」
  - 「当用户要求根据 Git 提交记录生成中文周报、周工作总结或迭代汇报时使用。」
- **错误（能力清单 / 流程剧透）**：
  - 「第一步盘点 diff，第二步分组，第三步 rebase，第四步校验……」

约束：中文，「当……时使用」格式，Frontmatter 总长 ≤ 1024 字符，包含自然触发词。

## 长度红线与拆分信号

| `SKILL.md` 行数 | 状态 | 动作 |
|---|---|---|
| < 200 | 健康 | 维持单文件 |
| 200–400 | 注意 | 监控篇幅，重复代码优先抽进 `scripts/` |
| 400–500 | 临界 | 评估拆分 `references/` |
| > 500 | **超限** | 必须拆分 |

**何时需要 `references/`**：
- **域知识密集型**（如 `dev-standards`、`vue-standards`，包含多个相互独立的技术面）→ 在正文配「按需阅读路径」表，按主题拆入 `references/`。
- **规则 / 流程 / 工具型**（如 `audit-loop`、`deep-thinking`、`lzy-review-work`、`linearize-commits`）→ 控制在 200 行以内，单文件足够。

## 脚本化原则

> 把可重复、容错要求高的确定性操作放进 `scripts/`，不要靠模型临场拼长命令。

- **适合抽脚本**：在正文占 >20 行的执行代码；进程管理、端口清理、数据库只读查询、复杂校验；需要参数化的操作。
- **适合留在正文**：简短调用示例（`<skill-dir>/scripts/xxx`）、工作流步骤编排、教学性反例表格。
- **脚本规范**：文件头带清晰用途、用法、参数和注意事项注释；只读脚本确保不产生副作用。

## 反例章节

反例（看似合理但错误的做法）是 skill 中信息密度最高的部分：
- 优先使用两列表格（`看似合理但错误 | 正确做法`），直击模型最容易偷懒或跑偏的陷阱，不写显而易见的常识。

## 公开仓写法护栏（去 AI 味、去黑话、去私有泄露）

1. **用通行工程语言，不自创黑话**：如果一个术语需要另附一张词典解释，就把它改写成普通开发者一看即懂的话。
2. **直白陈述规则与理由，少写防御性叠甲**：写清「做什么、为什么、边界在哪」即可，避免反复堆砌「不是 A 而是 B」「绝不意味着 C」的冗长套话。
3. **公共仓必须自包含**：不出现本机绝对路径、未公开的私有包名/仓库名/模型别名、真实私密业务案例，或指向仓外私有 skill 的硬依赖。
4. **保持中英文统一**：中文正文配合必要的英文技术标识符，不出现半篇英文半篇中文的拼接结构。

## 反模式清单

| 反模式 | 问题所在 |
|---|---|
| `description` 写完整流程或能力清单 | 模型跳过正文直接按描述执行 |
| 在正文另起「触发词」章节 | 与 L0 `description` 重复，浪费加载 token |
| `SKILL.md` 超过 500 行 | 触发加载成本过高，重点被淹没 |
| `reference` 嵌套 `reference` | 加载链路不清，易遗漏关键细节 |
| 正文内嵌大段可执行脚本 | 复制易出错且白耗 token，应抽到 `scripts/` |
| 隐式提及参考文档 | 不写明何时读取，模型不会主动加载 |
| 混入私有仓库路径、内部代号或私密案例 | 公开分享时无法追溯且存在泄露风险 |
| 用自创隐喻替代通用术语 | 增加理解成本，容易被模型望文生义 |
