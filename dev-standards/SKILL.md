# 前端开发通用规范（框架中立）

## 概述

一套面向前端项目（尤其是中后台、管理端与多模块 Web 应用）的工程规范，分为三层：**工程理念**（为什么这么设计）→ **目录与文件组织**（东西放哪）→ **代码内部约定**（具体怎么写）。

本规范不绑定特定框架，适用于 Vue、React 等主流前端技术栈；如果需要 Vue 3 + Element Plus 的自包含专版，可直接使用 `vue-standards`（无需先加载本 skill）。

## 按需阅读路径

| 使用场景 | 必读文件 |
|---|---|
| 做任何目录或架构判断前 | 先读本文件（工程理念 + 主分界规则） |
| 决定新建文件、组件、路由应该放在哪个目录 | 读取 `references/placement.md` |
| 编写请求层、列表页、表单、状态管理、组件通信，或处理加载/错误反馈 | 读取 `references/code-internal.md`（涉及页面交互必读其中的「界面优先呈现与布局稳定」） |
| 把规范转化为团队项目的 `AGENTS.md`，或处理 monorepo / 多宿主改造 | 读取 `references/localize.md` |

## 八条核心工程理念

| # | 理念 | 具体做法 | 反面做法 |
|---|---|---|---|
| 1 | **用模板和规则固化经验** | 把验证过的目录、工程配置和文档沉淀为可复用模板，新项目从成熟起点开始 | 每个新项目从零手配 |
| 2 | **生产项目是权威标准** | 模板只是阶段快照，定期把生产项目中打磨好的组件与约定反向同步回模板 | 模板和实际项目各自漂移 |
| 3 | **机制先行、配置后填** | 先搭好完整分支逻辑与占位结构（如先留空错误码数组但写完处理分支），运行期决策定下来后只填数据 | 等所有配置项敲定才写主流程 |
| 4 | **薄封装、插槽按名扩展** | 基础封装只统一声明方式（列配置、插槽名、类型定义），不接管页面的 loading、分页和数据请求职责 | 做出包揽一切、难以扩展的超级组件 |
| 5 | **用负面清单守住边界** | 明确写清「不做什么」（不做页面列表缓存、不用隐式通信、不建冗余中间层），比正面穷举更稳定 | 只列鼓励项，边界逐渐失控 |
| 6 | **开发示例与生产严格隔离** | 示例页、调试路由和调试菜单全部用环境变量条件注入，生产路由表出厂默认保持干净 | demo 页面或调试菜单混进生产包 |
| 7 | **把决策原因留进文档** | 重要设计取舍和踩坑根因写入文档，让人和 AI 都能直接读懂「为什么这样写」 | 只靠口口相传的隐式上下文 |
| 8 | **人在 IDE 中可直觉定位** | 目录结构优先保证开发者顺着目录树能直接翻到目标文件，全局搜索只是辅助 | 以「搜得到」为由容忍混乱目录 |

## 最核心的目录分界规则

> **跨页业务事实按「类型」集中；页面 UI 按「业务功能」共置。**

- **按类型集中**：API 请求函数、跨页接口类型、全局会话状态、多语言文案（i18n）、无状态纯工具函数、全局样式入口。
- **按业务共置**：页面主体、页面私有组件、私有子视图、页面私有静态资源、页面私有类型，统一放在同一个功能目录内。

**判断口诀**：**删掉这层页面 UI，这个文件还成立吗？** 成立 → 放类型集中目录；跟着页面同生共死 → 放页面功能目录。

## 跨框架通用的 10 条核心习惯

1. 每个页面或独立 UI 功能目录提供一个精简的 `index.ts` 对外入口（纯数据/工具目录不建聚合 barrel）。
2. 零业务语义的通用基础组件与带业务语义的复用组件物理分区，通用基础封装可用统一命名前缀作为区分信号。
3. 表格采用声明式列配置 + 自定义单元格插槽按名扩展，封装层不接管数据获取、loading 与分页状态。
4. API 按端点做薄封装、类型随行，一个接口一个函数，不建多余的业务 service 中间层。
5. 组件通信收敛为三条通道：props 下发、事件上抛、ref 实例方法（不滥用隐式注入或全局事件总线）。
6. 不缓存页面级列表数据，切回列表宁可重新查询，不留陈旧脏数据。
7. 业务组件保持唯一写法（Vue 统一 `<script setup>`，React 统一函数组件），组件名明确，模板/JSX 标签使用 PascalCase；底层错误边界按框架原生 API 实现。
8. UI 组件库样式通过项目内独立覆写层调整，不 fork 组件库源码。
9. 请求层统一接入错误码查表回退，并常备会话过期登出拦截位。
10. 保持仓库提交卫生：提交信息格式统一，不把锁文件（如项目约定不入库）、编辑器个人配置和构建产物提交进仓库。

## 界面体验主目标

**界面优先呈现，全过程保持布局与有效状态稳定**：不依赖远端数据且允许展示的页面框架和控件应先呈现，依赖数据的区域在原位置逐步填充；加载、刷新、成功、失败与消息提示均不得无故替换页面主体、撕裂布局或丢掉用户有效输入。详细规则与验证方式见 `references/code-internal.md` 的「界面优先呈现与布局稳定」。

## Vue 与 React 习惯对照

| Vue 侧习惯 | React 侧等价做法 |
|---|---|
| 功能目录提供 `index.ts` 对外入口 | 功能目录 barrel / 包公开入口（同样只在 UI 模块按需使用） |
| 不用 `provide/inject` 传业务流 | 不用 Context 传频繁变化的业务数据流（仅放全局不变配置） |
| 多 `v-model` 手写 `computed` get/set 代理 | 受控 `value` + `onChange`，避免隐式双向魔法 |
| 表格单元格按插槽名扩展 | `children` 或 render props 按列名路由 |
| `defineOptions({ name })` 显式命名 | 明确函数组件名 / `displayName` |
| 透传底层组件实例方法（`vm.exposed`） | `forwardRef` / `useImperativeHandle` 透传必要方法 |

上述对照反映等价的设计原则，不机械要求逐条照搬语法。

## 使用边界

本规范以个人工程习惯为基础整理；落地到具体项目时，项目自身的 `AGENTS.md` 或架构规则优先级高于本规范（尤其是宿主边界、包所有权与认证边界）。在团队协同或非本人主导的项目中，**仅当用户明确要求时**才应用本规范，不主动强加或大范围重构他人目录。
