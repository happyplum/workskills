# 代码内部约定（框架中立）

## 请求与错误管道

- **单一请求入口**：所有 HTTP 请求经统一封装层发出；业务状态码判定与会话过期处理集中在这里，业务调用点不重复写判断。
- **兼容 Mock 与真实后端的统一拦截**：开发 Mock 与真实后端响应格式不同时，在同一拦截层按特征字段是否存在区分处理，做到零代码改动切换 Mock 与真实服务，不维护两套请求代码。
- **错误码三级回退**：错误码映射表（值为 i18n 键名）→ 契约明确允许面向用户且不含敏感信息的服务端原始消息 → 默认兜底文案。不符合展示条件的原始技术信息直接跳过；带占位符的提示（如剩余次数、锁定分钟数 `{count}`）由响应 `data` 字段填充。
- **机制先行**：诸如强制登出错误码列表等待定配置，先以空数组 + 完整处理分支把机制写完整，后端确定码值后只需补配置。
- **HTTP 错误与业务错误分开处理**：网络或 HTTP 状态异常映射为统一服务错误码，与业务错误码分叉处理。
- **拦截器内延迟获取状态 store**：在请求/响应拦截器回调里按需获取状态管理实例，避开应用启动初始化顺序和循环依赖问题。

## 界面优先呈现与布局稳定

首要交互目标：**不依赖远端数据且允许展示的页面框架、导航、标题和控件应先显示，依赖数据的区域在原位逐步就绪；加载、刷新、成功、失败与消息提示均不得无故替换页面主体、撕裂布局或丢掉用户有效输入。**

> 权限/登录校验仍是受保护内容的前置条件，不可绕过校验先渲染敏感数据；也不必用定时器人为制造「先渲染再请求」的假象。

### 七条核心约束

1. **反馈与页面主体分离**：普通成功、警告或单接口失败，不要用顶层提前 `return` 或 `return null` 把整个页面、卡片或表单替换成一行错误文字，也不要往布局网格里临时硬插报错块撑变形。保留外层容器与无关区域，只让真正依赖失败数据的区域进入失败态；提示本身不得引起组件换 `key` 重建或丢失输入。
2. **按场景选对反馈形式**：按下方对照表选用轻量提示（Toast）、字段内联错误、局部状态区或对话框——不把所有错误都做成 Toast，也不把普通提示硬塞进正文。复用项目公共组件的可访问性能力（状态播报、字段错误关联、弹窗焦点管理）。
3. **保留有效状态，不伪造结果**：同一资源、筛选条件和身份下刷新失败且旧数据仍有效时，保留原内容并提示刷新失败（不跨页缓存、不拿旧筛选或旧租户数据冒充新结果）；表单提交失败必须保留用户输入和弹窗、结束提交 loading，不执行成功后的关闭/清空/跳转。严格区分「加载失败」「成功但无数据」「加载中」，禁止用空数组或默认值把失败伪装成空列表。
4. **副作用与通知归属单一**：Toast、弹窗等副作用在事件回调、请求完成回调或 Effect 等渲染外路径触发，严禁在组件渲染过程、`useMemo` / `computed` 或模板求值中直接调用。同一次失败只由一个明确层级弹出通知（避免拦截器、请求库和页面各弹一次），重渲染和自动重试不重复弹同一错误，但用户主动重试再次失败必须能收到新反馈。
5. **保留错误语义，控制崩溃传播范围**：遵循项目请求契约保留 `throw` / `reject` 或显式错误返回，禁止空 `catch` 吞错。核对路由边界、查询库、Suspense 和 Error Boundary 的传播范围，把局部失败留在局部处理，不轻易冒泡击穿整页。React 子组件渲染错误须靠 Error Boundary 捕获（不可靠包住 JSX 的 `try/catch`）；Vue 的 `errorCaptured` 捕获后也需切换到安全的降级视图，而非继续死循环重渲染报错子树。
6. **复用公共反馈能力与布局样式**：使用项目统一的提示 API 和布局规则，确保消息挂载容器不会随局部故障区域一起卸载。保持数据区失败态的合理空间，不坍塌变形；正文与通知只给用户可读文案，堆栈、原始响应和敏感信息只进脱敏日志。
7. **合理例外与改动边界**：遇到无权限、资源不存在、登录失效或页面无法安全继续时，按项目访问控制跳转到对应状态页，不强留页面展示越权或失效内容。修复问题时只改当前涉及路径，不趁机另起新框架或全仓重构。

### 不同场景的反馈选择

| 场景 | 推荐反馈方式与保留范围 |
|---|---|
| 初次进入，数据加载中 | 先呈现允许展示的页面框架和可用控件；数据区显示局部 loading 或骨架屏并占位，数据回来后原地更新 |
| 普通操作结果（无字段级承载） | 轻量 Toast / Message；保持主体不动；主动取消或已过期的请求不报失败，超时按失败处理 |
| 首次加载失败，无可用数据 | 保留外层布局与可用控件，在原数据区显示简短失败状态与重试入口；不能只靠一闪而过的 Toast，也不能伪装成「暂无数据」 |
| 已有数据，刷新失败 | 保留当前仍可用的数据并明确提示刷新失败；持续异常时在既有状态区提示 |
| 表单字段校验失败 | 错误直接关联到对应字段，保留用户输入；需要汇总时用表单错误摘要，不强制再弹 Toast |
| 持续离线或部分服务不可用 | 使用既有状态槽或持久 Alert / Notification，不依赖自动消失的 Toast |
| 需要用户确认或选择后才能继续 | Modal / Dialog；保留底层页面并管好焦点，普通失败不滥用模态框阻断 |
| 子树渲染崩溃 / 访问受限 | 分别按 Error Boundary 或访问控制页降级；保留安全外层区域，恢复操作须真实可用 |

### 框架落地注意点

- **React**：条件提前返回本身不是错，错在把不该隐藏的外层布局一起拦掉了；数据区内部展示错误态完全合理。业务组件统一函数式写法，但底层 Error Boundary 仍遵循 React 类组件或成熟库实现，优先复用项目已有边界。
- **路由与查询库（React Router / TanStack Query 等）**：按项目实际版本确认错误传播机制——查询函数用 `throw`/`reject` 标识失败，是否抛给渲染边界是另一回事（如 TanStack Query v5 的 `useSuspenseQuery` 需结合局部边界使用）；使用 Suspense 时同样把边界放在局部数据区，不替换整页框架。
- **Vue**：`errorCaptured` / `onErrorCaptured` 捕获异常后，不保证出错组件能继续安全渲染，需配合局部降级展示。

### 界面改动短程验收要点

按实际改动范围验证，不要求无关页面跑全量测试：
- 模拟短暂延迟：页面框架先显示，数据分批原地填充，无整页重建、明显布局跳动或输入丢失。
- 模拟首载失败 / 刷新失败 / 提交失败：外层容器完好，错误与空态区分明确，输入与弹窗保留，loading 正常结束，不重复弹 Toast。
- 局部渲染异常：受影响区域降级，外层完好，点击重试可真实恢复并清除旧错误态。
- 视觉与交互变更须在浏览器核对受影响区域的主题、尺寸、长文案和焦点管理，不能仅靠单元测试代替。

> 底层运行机制参考各框架官方规范：React（Error Boundary、渲染纯度、状态保留、Suspense）、React Router（Error Boundary）、TanStack Query（Query Functions / Suspense）、Vue（`errorCaptured`）、W3C WCAG 2.2（状态消息与错误识别）。

## 表格与列表页约定

- **声明式列配置 + 插槽按名扩展**：通过 `columns` 数组声明列信息，自定义单元格在列配置里声明插槽/渲染位名称，外部按名填充，封装组件无需反复改代码即可扩展。
- **薄封装不抢职责**：表格组件不持有 loading、空态、分页状态或请求逻辑，全部由页面传入；页码变更与每页条数变更合并为单一 `change(page, size)` 事件。
- **列显示配置持久化**：按表格 ID 本地保存列显示隐藏与排序；列标识未指定 `prop` 时用 `label` 兜底。
- **透传底层实例方法**：封装组件透出必要的底层表格实例方法（Vue 透传 `exposed` / React `forwardRef`），不逐个手写重复代理。
- **列表页标准五步骤**：
  1. 查询表单与分页状态留在页面内部（不进全局 store）；
  2. `query()` 先把页码重置为第 1 页再请求（修改筛选即回首页）；
  3. 统一的 `changePage(page, size)` 分页处理函数；
  4. 用 `try / finally` 托管 loading 状态，确保异常时也会关闭；
  5. 重置动作 = 逐字段还原初始值 + 回第 1 页 + 重新查询。
- **入参在边界只转换一次**：例如日期范围转 ISO 字符串，统一在组装请求参数时转换一次，不在 UI 展示层来回转换。

## 表单与弹窗约定

- **新增 / 编辑 / 详情共用一个表单组件**：靠路由参数或显式模式区分状态，项目内必须统一唯一一种模式判断方式，不混用多种判断写法。
- **字段级禁用支持业务叠加**：采用 `:disabled="isDetail || <业务状态>"` 放在字段级，比整个表单一刀切禁用更灵活，能表达详情态与业务态叠加。
- **校验规则就地编写**：跨字段校验通常依赖闭包访问当前表单其他字段，规则写在表单组件内更清晰；多卡片表单共享一份数据模型、按区分别校验；触发时机默认输入用 `blur`、选择用 `change`。
- **弹窗两态管理与彻底重置**：用 `visible` + `type`（新增/编辑/详情）管理状态；`destroy-on-close` 只销毁 DOM 和校验态，**响应式数据模型必须手动重置**；编辑时只浅拷贝所需字段，防止直接修改列表原行数据；右上角关闭、点遮罩和点取消统一走关闭前钩子清理草稿。
- **提交必须带 loading，成功后回到第 1 页刷新**：提交按钮使用 `try / finally` 控制 loading；提交成功后关闭弹窗并触发列表回到第 1 页重新查询，让用户直接看到新增/更新结果。

## 状态管理与缓存原则

- **全局 store 准入严格**：只放跨页面共享的会话与导航状态（当前用户、菜单权限、访问标签历史）；列表筛选、分页、表单和弹窗态一律留在页面内。
- **不做页面级列表缓存**：不用 `keep-alive` 缓存业务列表页；多标签导航只记录路径，切回页面直接重新拉取最新数据，避免脏缓存引发隐蔽 bug。
- **会话态随标签页生命周期管理**：认证与会话信息优先按 `sessionStorage` 语义管理；登出时直接调用 `sessionStorage.clear()` 整仓清空，后续新增缓存键自动被覆盖，不用维护易遗漏的逐键清理清单。
- **多租户职责拆分**：身份所属租户放进认证凭证（token），业务查询的数据范围放进各页面请求参数显式声明，不做隐式全局注入。

## 组件通信纪律

- **收窄为三条显式通道**：props 下发、事件上抛、ref 实例方法。除此之外不新增隐式通道（Vue 不用 `provide/inject` 和全局事件总线；React 不用 Context 传递业务数据流）。
- **受控代理显式书写**：多字段双向绑定手写 `computed` 代理或 `value + onChange`，不用隐式语法糖掩盖数据流。
- **命名与暴露最小化**：同类 loading 命名保持一致（如 `tableLoading`）；封装组件只对外暴露必要的实例方法（如 `open()`、`resize()`），内部状态保持私有。

## 负面清单（明确不做什么）

- 不做页面级列表缓存（如 `keep-alive` 缓存业务列表）。
- 业务组件不混用旧式写法（Vue 统一组合式，React 统一函数组件；底层错误边界按框架原生要求除外）。
- 不用 URL query 参数传递实体唯一 ID（改用路径参数 `/:id`）。
- 不向仓库提交编辑器个人配置、构建产物以及项目约定忽略的锁文件。
- 迁移或重构完成后及时删除旧兼容层、双写和废弃字段兜底，不留历史包袱。
- 不建无实际聚合价值的业务 service 中间层，API 薄封装直接供页面调用。

## 工程工具链偏好

- **Git 卫生**：统一提交前缀格式与分支命名规范，合并前压缩过多细碎提交。
- **Lint 分工**：快速静态扫描器先行，ESLint 负责深度规则兜底，代码格式交给 formatter 统一处理。
- **构建信息注入**：构建时注入 git commit、branch、构建时间，并挂一个控制台可调查看函数，线上排查版本零成本。
- **开发代理零路径改写**：前端请求前缀与后端路由前缀对齐，按服务前缀分流代理，不做复杂路径 rewrite。
- **UI 库按需引入注意补样式**：模板自动按需引入通常覆盖不到脚本里手动 `import` 的反馈组件（如消息提示、弹窗），手动引入时记得检查样式是否已按需加载。
- **运行时主题派生**：基于主色通过算法动态派生亮/暗色阶写入 CSS 变量，不手动硬拷贝整套色板。
