# 落位层：东西放哪（框架中立）

## 主分界规则

业务事实按种类集中；UI 按业务共置。

| 去向 | 装什么 | 例子 |
|---|---|---|
| 种类集中区 | API 声明与类型、全局/会话状态、文案、无状态工具、全局样式入口 | apis/、types/、stores/、locales/、utils/、styles/ |
| 业务共置区 | 页面、页面私有组件、私有子视图、私有静态资源、页面私有类型 | views/children/<feature>/ |

例外边界（考古结论，三分法）：API 函数**永不**共置（恒在种类区）；类型两分——跨页共享类型集中种类区、页面私有类型共置 feature；组件/页面私有静态小资源（图标等）共置。

## H1–H11 全文（规则 | 为什么 | 禁止读法）

### H1 路由即地图
- 规则：从路由入口出发，人能在 IDE 里 **≤3 跳**找到拥有该 URL 的页面文件；路由元数据（标题/i18n 键/图标）贴着路由身份放。
- 为什么：路由表是产品地图，是人定位页面的第一入口。
- 禁止：路由表膨胀成第二可写身份源；元数据散落 5+ 处；隐式跨文件默认路由。

### H2 路由分册 + 宿主装配
- 规则：按业务域各维护一册路由/身份表（settings 一册、chat 一册），宿主/应用入口 import 后**自行装配**（挂哪些册、接 history、本地 overlay）。路由表与菜单表分职，菜单可聚合多路由。
- 为什么：分册让域内自治，装配权留宿主，跨宿主不泄漏。
- 禁止：共享分册展开某宿主私有路由；菜单表反向长出第二路由身份。

### H3 选择性窄门口
- 规则：UI 单元（页面、feature 目录、组件目录）提供一个窄入口文件；消费者经门口导入。种类集中区（api 客户端、store、types、locales、utils、styles）**不**设 barrel。
- 为什么：门口降低跳数、收窄公共面；技术区 barrel 只会增加中间层。
- 禁止：门口膨胀成 fat barrel；多层转发藏 owner；穿透门口直捣内部文件。

### H4 公共组件三区
- 规则：(a) 通用能力区——可拷任意项目、零业务语义；(b) 跨页业务复用区——带产品语义随应用走；(c) widget/仪表盘特区。业务件永不进通用区；两个宿主不得平行实现同一业务 UI。
- 为什么：三区对应三种复用半径，混区会让「能不能拷走」失去判据。
- 禁止：命名前缀（如 DM）标在业务件上；为「以后可能复用」提前抽公共（指**业务复用区**——能力件判定见 H9 与口诀：单页使用也须判一次可移植性，不受「第二调用方」限制）。

### H5 先分类后落位
- 规则：新文件先回答三问——宿主归属？业务归属？复用层级（页内私有/跨页业务/通用能力）？——然后落位。
- 为什么：跳过分类必靠「离调用近」落位，结构随调用点漂移。
- 禁止：以调用点邻近代替归属判断。

### H6 目录纯度（已降级）
- 规则：只要求**高频业务目录**类别清晰可数；技术目录（生成代码、协议适配、基础设施）不强求纯净。
- 为什么：考古证实连本人旧项目的技术区也不绝对纯；为纯度加空壳目录是负资产。
- 禁止：为形式纯度拆散内聚业务、增加转发层。

### H7 人能顺着翻到
- 规则：关键业务路径必须**不依赖全局搜索**即可逐层定位。
- 为什么：人优先——让 AI 适应人比人适应 AI 便宜；AI 能搜到不等于结构合格。
- 禁止：用「AI 能搜到」为不可导航结构辩护；要求所有底层设施同等直观（只管关键路径）。

### H8 同类别同构
- 规则：同类页面/模块在不同业务下内部组织一致（同类 section 同构、同类列表同构）。
- 为什么：同构让「见过一个就会翻第二个」，认知成本一次付清。
- 禁止：为表面一致抹平真实边界（宿主、包所有权、Worker 边界）。

### H9 页内私有件共置
- 规则：页面私有组件/状态/资源默认进页面文件夹。能力件（富文本、日期选择类）即使当前只有一页用，也要单独判一次「剥掉业务还成立吗」：成立 → 通用区；不成立 → 留页内。出现第二个调用方才抽业务复用区。
- 为什么：未证实复用就抽公共是最大漂移源；能力件手感私有、实质公共，需显式判断。
- 禁止：以「现在只有一页用」把明显能力件永久私有化。

### H10 布局协议层
- 规则：全局壳唯一（侧栏/内容/顶栏）；页面用槽位化结构协议——表格页协议（搜索区/操作区/内容区）、表单页协议（头/右上/体/脚）——协议可嵌套。登录在壳外。
- 为什么：协议让页面结构成为肌肉记忆，新页面不再自编骨架。
- 禁止：每个页面即兴编排结构；把协议做成拥有业务数据的大组件。

### H11 命名法典
- 规则：文件夹 camelCase；路由 path 全小写拼接；组件名 PascalCase；语义后缀 Form/Detail/Tab/Modal/Section；路径参数用 /:id 不用 query。同一 codebase 一套体系。
- 为什么：命名是最低成本的自动分类信号。
- 禁止：同一层混用多种 casing；用 query 承载实体身份。

## 新文件落位决策树

1. 是某宿主/平台私有能力？→ 宿主区
2. 删掉 UI 还成立（零业务语义）？→ 通用能力区
3. 只服务一个页面？→ 该页面文件夹（共置）
4. ≥2 页面/宿主复用且带业务？→ 业务复用区
5. 是业务事实（API/类型/文案/全局态）？→ 对应种类集中区
6. 都不是 → 先别建文件，先补分类判断（回到 H5）
