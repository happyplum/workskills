# 目录与文件组织规范（框架中立）

## 主分界规则

**跨页业务事实按类型集中；页面 UI 按业务功能共置。**

| 归属区 | 存放内容 | 常见目录示例 |
|---|---|---|
| 类型集中区 | API 函数、跨页接口类型、全局会话状态、多语言文案、无状态工具、全局样式入口 | `apis/`、`types/`、`stores/`、`locales/`、`utils/`、`styles/` |
| 业务共置区 | 页面文件、页面私有组件、私有子视图、页面私有小资源（如图标）、页面私有类型 | `views/children/<feature>/` 或 `features/<feature>/` |

**细分边界**：
- API 请求函数始终放类型集中区，不散落在页面目录；
- 类型分两种：跨页共享类型放集中目录，只服务单页的私有类型跟页面共置；
- 页面私有组件和私有小资源直接跟页面共置。

## 目录与结构规则

### 1. 路由即产品地图
- **规则**：从路由入口文件出发，开发者在 IDE 里最多跳转 3 层就能定位到该 URL 对应的页面文件；路由元数据（标题、国际化键、图标等）紧贴路由定义存放。
- **原因**：路由表是新人或自己回看项目时定位页面的第一入口。
- **禁止**：维护多份彼此竞争的路由配置；把同一页面的标题/路由键散落写在 5 个以上文件里；使用难以追踪的隐式自动路由覆盖。

### 2. 路由按域拆分、由应用入口装配
- **规则**：按业务域分别维护路由定义文件（例如设置域、聊天域各一份），由具体应用或宿主入口引入后决定挂载哪些路由、接入哪种 history 以及叠加宿主专属页面。路由表与菜单表职责分离，一个菜单项可以聚合多个子路由。
- **原因**：业务域内高内聚，装配权留给应用入口，多端/多宿主复用时不会互相泄漏私有页面。
- **禁止**：在共享路由模块里硬塞某个宿主专属的私有路由；让菜单配置反向充当路由身份真源。

### 3. UI 模块使用精简入口，类型集中目录不建聚合 barrel
- **规则**：页面目录、功能模块目录或复杂组件目录提供一个精简的 `index.ts` 对外入口（只做必要的公开导出，不写业务逻辑），外部调用方通过该入口导入。API、store、types、locales、utils、styles 等按类型集中的目录**不**建立大而全的聚合 `index.ts`。
- **原因**：UI 模块统一入口可以隐藏内部拆分子文件、缩短导入路径；而在纯工具或 API 目录建大 barrel 只会增加中转层，容易引发循环依赖和打包膨胀。
- **禁止**：把入口文件写成几十行多层转发的「臃肿 barrel」；外部绕过模块入口直接深层导入其私有子文件。

### 4. 公共组件分三区
- **规则**：公共组件按复用半径严格分成三个区域：
  1. **通用基础组件区**：零业务语义、可直接复制到其他项目的组件（如二次封装的表格、日期选择、富文本、图表）；可用统一命名前缀作为基础能力标识。
  2. **跨页业务复用区**：带产品业务语义或接口调用、被多个页面或宿主复用的组件（如登录框、权限树、业务上传弹窗）。
  3. **仪表盘小组件区（Widget）**：专供工作台/仪表盘拼装的独立卡片挂件。
- **原因**：三类组件的依赖边界和可移植性完全不同，混在一起会让开发者分不清哪些组件能独立复用。
- **禁止**：给带业务语义的组件加上通用基础前缀；因为「以后可能会复用」就提前把单页业务组件抽进跨页复用区；在多宿主项目中各自平行实现一套相同业务 UI。

### 5. 先判归属，再建文件
- **规则**：新建任何文件前先回答三个问题：① 属于哪个应用/宿主？② 属于哪个业务域？③ 复用层级是页面私有、跨页业务还是零业务通用能力？答完再决定落到哪个目录。
- **原因**：跳过分类直接「离当前编辑的文件近就放旁边」，会导致目录随开发顺序持续漂移。
- **禁止**：仅凭「顺手」或「离调用点近」决定文件位置。

### 6. 高频业务目录保持清晰，不强求底层技术目录形式纯洁
- **规则**：高频访问的业务功能目录必须分类清晰、一眼可数；代码生成目录、协议适配层、底层基础设施目录允许按技术现实组织，不为了表面整齐强行拆分。
- **原因**：为了形式纯度给底层技术目录套空壳子目录只会增加跳转负担，没有实际收益。
- **禁止**：为了凑目录整齐而强行拆散高内聚代码或增加无意义的转发层。

### 7. 关键业务路径在 IDE 目录树中可直觉翻到
- **规则**：核心业务页面和主流程文件，必须在不依赖全局全文搜索的前提下，顺着目录树逐层就能找到。
- **原因**：让代码结构适应人的心智模型成本最低；AI 搜索很快，但不能拿「搜得到」替糟糕的目录辩护。
- **禁止**：把所有文件平铺堆在一起或按晦涩代号命名目录；同时也不必强求所有底层工具与业务目录同等直观，管好关键业务路径即可。

### 8. 同类页面/模块保持一致的内部结构
- **规则**：属于同一类型的页面或分区（例如多个设置子页、多个管理列表页）采用一致的文件拆分和命名结构。
- **原因**：看懂一个页面的组织方式，就能立刻上手其余同类页面，降低长期维护成本。
- **禁止**：为了表面长得一样而强行抹平真实架构边界（如宿主隔离、独立包所有权、Worker 进程边界）。

### 9. 页面私有物默认共置，按实证时机再上提
- **规则**：只服务当前页面的子组件、私有状态和静态小资源默认留在页面目录内。
  - **跨页业务组件**：直到**第二个实际调用方出现**时，再上提到跨页业务复用区。
  - **零业务通用能力组件**（如富文本编辑器、通用日期选择器）：即使当前只有一页使用，也要主动判断一次「剥掉当前业务的文案和接口后，它还成立吗？」成立就放通用基础组件区，不成立则留页内。
- **原因**：凭猜测提前抽象公共业务组件是目录腐化的主要源头；而明显通用的能力组件如果一直埋在某个业务页里，后续极易被人重复造轮子。
- **禁止**：因为「现在只有一页用」就把明显零业务的通用能力组件永久藏在某个业务目录里。

### 10. 统一布局容器协议
- **规则**：应用全局只保留一个主布局外壳（侧栏 / 顶栏 / 主内容区），登录页等独立入口在主壳之外；常规业务页使用统一的槽位化布局组件（如表格页提供搜索区/操作区/内容区，表单页提供头部/操作区/表单体/底部操作栏），复杂页面允许布局嵌套。
- **原因**：统一布局骨架让新页面无需反复手写重复结构，视觉和交互自然一致。
- **禁止**：每个页面各写一套边距和框架结构；把纯布局容器做成吞并业务数据的重型组件。

### 11. 统一命名规则
- **规则**：同一代码库坚持一套命名体系——功能文件夹 `camelCase`，路由 path 全小写拼接，组件名 `PascalCase`，按角色附语义后缀（`Form`、`Detail`、`Tab`、`Modal`、`Section`），实体 ID 优先通过路径参数 `/:id` 传递而不是塞进 query。
- **原因**：命名是成本最低的自动分类信号，看文件名就能知道职责。
- **禁止**：同一层目录混用多种大小写风格；用 query 参数承载实体唯一身份。

## 新文件归属速查决策树

按顺序从上到下判断：

1. 属于某个特定宿主或平台私有能力？ → 放对应宿主目录
2. 剥离业务文案与接口后仍然独立成立（零业务语义）？ → 放通用基础组件区
3. 目前只服务单个页面？ → 放该页面功能目录（共置）
4. 已被 ≥2 个页面或宿主复用，且携带业务语义？ → 放跨页业务复用区
5. 属于跨页业务事实（API / 共享类型 / 文案 / 全局会话状态 / 纯工具）？ → 放对应类型集中目录
6. 以上都无法确定 → 先停下来补清归属判断，再建文件
