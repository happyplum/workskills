# 规范落地指南：转成项目规则与大型仓库改造

## 何时落地为项目规则

- **个人独立项目**：直接按需加载本 skill 即可，不必把全部条款复制进项目仓库。
- **团队协同项目（多人或多 AI 协作）**：仅当用户**明确要求**把规范固化进项目时，再提炼适用条目写入项目的 `AGENTS.md`（或团队约定的规范文档）。未经用户明确要求，不主动改写他人或团队的治理文件。
- **优先级原则**：一旦落地，项目内 `AGENTS.md` 成为该项目的本地版本；若与本 skill 通用条目冲突，以项目自身的宿主边界、包所有权与安全约束优先。

## 落地步骤

1. **按需裁剪**：目录与文件组织规范通常整体适用；代码内部约定按项目实际形态选取（例如没有管理端表格就不必搬运表格协议）。
2. **写成可核查的项目条款**：每条用项目自身目录名改写，保留「规则一句话 + 原因一句话 + 可核查的验收方式」（例如用命令或正则检查「所有功能目录都有 `index.ts`」「不存在绕过入口直接导入内部文件」）。
3. **置顶项目硬边界**：先把宿主隔离、包边界、认证与路由唯一来源等项目级架构约束写清楚，并明确其优先级高于编码风格习惯。
4. **标明豁免范围**：明确写出代码生成目录、底层协议适配目录等豁免条款，避免协作者或 AI 机械套用规则、造出空壳目录。
5. **配置自动化检查**：把目录入口、命名或禁用导入这类机械规则做成脚本接入 CI，防止后续回潮。

## Monorepo / 多宿主仓库改造边界

在大型 monorepo 或多端宿主（如 Web + 桌面端）仓库中应用本规范时，牢记：**包边界、宿主隔离和进程/Worker 边界属于真实运行时约束，不能为了目录手感强行压平。**

### 必须保护的六条边界

1. **单一路由身份源**：可以按业务域拆分路由文件，但必须与既有路由体系保持同源或清晰主从，不能造出两张互相竞争的可写路由表。
2. **共享路由不泄漏宿主私有页**：宿主专属的本地设置或平台私有页面留在各自宿主目录，由宿主装配时叠加。
3. **核心数据事实单源**：接口类型、令牌生命周期、用户配置等各有唯一维护方，整理目录入口不得制造第二份副本。
4. **底层技术目录免于形式苛求**：Worker、协议转换、自动生成代码等目录不强求与业务目录一样整齐。
5. **只在 UI 模块建入口**：不给 API/store/utils 等类型集中目录造聚合 barrel，不为了统一而新增冗余 service 或 facade 层。
6. **禁止平行重复实现**：整理结构不得演变成两个宿主各自复制维护一套相同的业务界面。

### 大型仓库渐进改造优先级

1. **先给高频业务目录补统一入口**：最快解开跨目录深层导入网，收益最高。
2. **再统一同类页面的内部组织**：让同类列表页或设置分区保持一致结构。
3. **归拢散落的路由元数据**：把散在多处的菜单标题、图标、国际化键收拢到路由定义旁。
4. **最后统一命名**：纯机械改动，可配合脚本批量完成，风险最低。
5. 每完成一步即补齐对应检查脚本；过渡期新代码严格走新入口，旧深层导入随改随修。

### 与项目既有规范的关系

如果项目已有更严格的工程守卫（如包边界校验脚本、特定安全存储要求），始终以项目既有守卫为准；本规范仅作为提升日常开发可读性与一致性的补充层，不覆盖安全与架构红线。
