# 落地：转成项目规则 / monorepo 改造裁决

## 何时落地

团队协同（多人、多 AI）**且用户明确要求把个人规范落地**时，适用条目才转写进项目治理文件（AGENTS.md 或等价物），让所有协作者与其 AI 和你的架构习惯一致；未经用户明确要求，不主动转写、不建议改写项目治理文件。个人项目可直接引用本 skill 不必落地。落地后：**项目规则是本地版，本 skill 是主版本**；项目特有边界优先于通用条目。

## 落地步骤

1. **挑层**：落位层（placement.md）全量；代码内部层按项目场景裁剪（没有表格域就不搬表格协议）。
2. **改写**：逐条转成项目语气——规则一句 + 为什么一句 + **验收锚**（可 grep 的结构断言，如「settings 各 section 均有 index.ts 门口」「无组件穿透门口导入内部文件」）。
3. **显式写边界**：宿主边界、包所有权、路由身份单源等项目事实写入，优先级高于通用条目。
4. **标注降级项**：H6 纯度、H7 非关键路径等已降级条目写明适用范围，防止被过度执行（为纯度加空壳目录）。
5. **配守卫**：结构性规则配检查脚本进 CI，防回潮。

## monorepo / 双宿主改造裁决

前提：包边界、宿主边界、Worker/进程边界是**真实运行时成本**，不在习惯改造范围内。习惯改造只动「人侧 DX」。

### 边界保护清单（不得为习惯压平）

1. **单一路由身份源**：可新增按域分册（settings 册 / chat 册），但必须与既有身份表同源或明确主从——禁止第二张可写身份表竞争。
2. **共享分册不展开宿主私有路由**；宿主 overlay（本地设置、平台私有页）留在宿主区。
3. **事实单源**：API 类型、token 生命周期、Profile 各有唯一 owner；门口化/同构化不得制造第二事实源。
4. **技术目录豁免纯度**（H6 降级区）：Worker、协议适配、生成代码目录不强求纯净，不为整齐重排。
5. **门口只加在 UI 单元**：不给种类集中区造 barrel；不建业务 service 中间层；不新增 facade。
6. **不平行实现**：习惯改造不得导致两个宿主各自实现同一业务 UI。

### 改造优先级参考（大型仓库通用顺序）

1. 高频业务目录**门口化**（H3）——先解深导入网，收益最大
2. 同类业务**同构化**（H8）——统一 section/列表内部组织
3. 路由**元数据归拢**到路由身份旁（H1）——消灭散落 5+ 处的标题/键
4. **命名统一**（H11）——最后做，纯机械、可脚本化
5. 每步配结构守卫脚本；改造期间新旧混用时以门口为新准则，旧深导入随触随修

### 与项目既有规范的关系

项目已有更严格的治理（如包边界回归脚本、token 存储约束）时，以项目治理为准；本 skill 条目作为人侧 DX 补充层，不覆盖安全/边界约束。
