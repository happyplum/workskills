# 中文周报生成器

## 概述

基于 Git 提交历史与可核实的代码证据，生成一份**可直接发给领导、无需再改写**的中文书面周报。核心目标是说清「本周交付了什么」「为什么重要（已验证的原因、机制或关键能力）」「还有什么未完成」。提交次数只是辅助证据，不是周报正文。

> **只读约束**：取证与生成过程完全只读，禁止修改产品代码、项目文档、Git 历史、分支，也不要在仓库内创建临时文件。

## 统计时间范围

用户未指定日期区间时，默认统计范围为 **上周日到今天**（含起止两天），不要强行截断成「上一个完整的周日到周日」。

- **结束日期（`end`）**：当前本地日历的今天（至 23:59:59）。即使今天是周一到周六，也**绝不**把结束日期回退到上周日。
- **起始日期（`start`）**：严格早于今天的最近一个周日。如果今天恰好是周日，起始日期为 7 天前（上周日），而不是今天。

示例（按本地日期）：
- 今天是周四 9 月 10 日 → `9 月 6 日（上周日）— 9 月 10 日（今天）`
- 今天是周日 9 月 13 日 → `9 月 6 日（上周日）— 9 月 13 日（今天）`
- ❌ 错误：今天是周四 9 月 10 日，却统计 `8 月 30 日 — 9 月 6 日`（漏掉了本周全部工作）

**显式区间优先**：用户只要明确给了范围（如「8 月 9 日到 8 月 16 日」「上周」「从某日到某日」），一律按用户指定的范围统计。如果措辞存在两种明显不同的理解，先问一个简短澄清问题再采集数据。

统计范围只在周报标题写一次，不要在每条工作项里重复贴日期。

## 作者与 Git 范围

1. **确认作者身份**：优先使用用户提供的姓名/邮箱；用户只说「我的提交」时，检查 `git config user.name`、`git config user.email` 以及近期提交作者。仅当存在多个可能作者且会明显改变统计结果时再询问确认。
2. **覆盖所有分支并去重**：默认加 `--all` 扫描，避免漏掉功能分支上的工作；按 commit hash 去重。
3. **默认按 author date 过滤**：author date 反映实际开发时间；仅当用户明确要求「提交时间」或「合入时间」时改用 committer date。若两者统计差异较大，可在必要时用一句说明解释原因。
4. **剔除非真实交付的 Git 记录**：stash 对象、纯 merge 记录、跨分支 cherry-pick 的重复补丁不作为独立工作项。
5. **不拿 commit 数量衡量产出**：一次架构改动可能跨越很多次提交，而后续修补可能属于同一项交付。

## 安全的 Git 采集方式（兼容 Windows / PowerShell）

避免在 PowerShell 中因为中文 commit subject 编码或变量赋值导致丢行、合行：

- 统计和过滤优先只输出 commit hash 和日期（或用 `git rev-list --count`），不要直接把带 `%s` 中文标题的 `git log` 赋给 PowerShell 变量来数行数。
- 先收集去重后的 commit hash 列表，再按需查看提交标题、改动路径、增删行数和关键 diff；不要在仓库目录内落盘中间文件。
- 抽查有代表性的 diff 和核心改动文件，核实每项交付的真实结果与技术原因；不必对几百个提交逐一通读全量 diff。

至少核实以下五项基础事实：
- 确认后的作者身份；
- 起止日期（含两端）与所用时间口径；
- 去重后的匹配提交集合；
- 主要涉及的模块、页面、脚本、测试与文档；
- 如存在分支重复、stash 或日期口径差异导致的数量偏差，记录原因备用。

## 独立交付聚类原则

先按**可独立向领导汇报的业务交付**把提交归组，最后自然得出条目数。绝不能先拍脑袋定一个条数，再反向硬合并去凑数。

**必须拆成独立条目**（满足任一即可）：
- 核心交付对象不同，各自本身就能作为完整事项向领导汇报（例如：登录页改造 vs 订单导出 vs 权限配置）；
- 即使对象相同，但业务意图、验收结果或发布/回滚边界彼此独立。

**允许合并为同一条目**：仅当这些提交服务于**同一个交付对象、同一个意图、同一个验收结果**。围绕该交付的界面样式、状态保存、单测与修复都归入该条目，不要拆成流水账式的开发步骤。

- 同一目录、同一天、同一作者、同一大模块，或为了「控制条目数量」，**都不是合并理由**。
- **文风反馈绝不改变聚类**：如果用户反馈「像流水账」「不专业」「太啰嗦」，**只能改写措辞、删减废话**，不得趁机合并、拆分、重排或删除独立工作项（除非用户明确点名要删或合并某条）。
- 配套的文档、测试或规则更新随它支撑的交付一起归组；如果文档或工程基建本身就是独立交付（如构建提速、发布流程改造、新增接口规范），单独成条并直接写明交付对象，不用「文档与治理」这类空泛兜底标题。

## 书面汇报文风（去注释腔、去流水账、去空转）

周报是正式的**书面工作汇报**，既不是代码注释的中文翻译，也不是口头演示故事。

- **标题**：回答「本周交付了什么」，统一用 `新增 / 调整 / 补齐 / 修复 + 主要交付对象`。
  - 一条标题只写一件事，不用分号把两件交付拼在一起；
  - 不写裸模块名（❌ `侧栏模块：响应式重构`），也不写附带结果/性状（❌ `工作模式引导可记住`、`登录改为独立页，选完空间再进主界面`）；
  - 正确写法：✅ `新增新手引导流程`、✅ `调整工作面板为浮动布局`、✅ `新增独立登录页`。
- **正文**：必须补充标题里没有的**已验证新事实**，禁止同义复述标题。
  - **修复类**：优先写「已验证的主因或关键机制 + 直接结果」（证据不足时写已验证机制，不编造唯一根因）；
  - **新增 / 调整 / 补齐类**：写「核心能力 + 业务结果」；
  - 附带特征（如“按账号记住状态”“不随滚动移位”“不再遮挡菜单”）写在正文里，不要塞进标题。
  - 可以保留产品名和用户可见的功能名，但**函数名、文件名、内部类型名、配置键名**不要写进正文。

### 交稿前四道检查

| 问题类型 | 反例 | 为什么不合格 | 正确书面汇报 |
|---|---|---|---|
| **注释话** | 将侧边面板改为 floating overlay，防止 scroll 事件带走 | 把代码实现手段当汇报，像 commit 备注 | 标题：`调整侧边面板为浮动布局`<br>正文：面板改为悬浮层展示，不再占用主内容滚动区域。 |
| **口语流水账** | 流式消息以前经常后到的先出来、跳着刷，这次改成按顺序出字就好了 | 用「以前…这次…」讲过程故事，夹带口语比喻（闪一下/被带走/糊成一块/跳着刷/点进去） | 标题：`修复流式消息乱序`<br>正文：展示顺序未与到达顺序对齐，后到达的片段会提前渲染。现已按到达顺序依次输出。 |
| **正文空转** | 标题：`修复长列表滚动定位`<br>正文：修复了长列表滚动定位不准的问题。 | 盖住标题后正文没有任何新事实，只是同义重复 | 标题：`修复长列表滚动定位`<br>正文：底部叠加了两层留白，且未渲染区域按估算高度占位导致总高度偏高。现已统一按实际容器高度计算底部空间，定位与跳转恢复准确。 |
| **标题性状化 / 拼凑** | `新增引导可按账号记住；调整面板不随滚动遮挡` | 把性状当标题，且把两件独立交付拼成一条 | 拆成两条：`新增新用户引导`（正文写按账号记录已读状态）、`调整侧边面板为浮动布局`（正文写浮层展示且不遮挡内容）。 |

### 用词自查清单

- 不要把「以前会…现在…这次…」当默认句式，只在对比本身就是核心结果时简短写一句。
- 避开口语化比喻（闪一下、盖一层、被带走、糊成一块、打架、跳着刷）与操作说明腔（点进去、还要再点一遍、这是预期不用担心）。
- 「实现了 / 将 X 改为 Y」后面如果接的是内部模块、函数或配置键，整句重写；接用户可见入口或功能可以保留。
- 避免用「保证 / 避免 / 防止 / 以便」拖长主句，直接写客观结果（写「不随页面滚动」，不写「防止被滚动带走」）。
- 避免「显著提升」「彻底解决」「加强了稳定性」「优化了体验」等无证据空话，只写证据能支撑的具体可观察结果。
- 未完成的验收或遗留事项用客观书面语附在同一条末尾（如「目前尚未完成浏览器兼容性走查」），不单独开「风险与后续」章节，也不编造积极总结套话。

## 默认输出格式

直接输出可粘贴使用的中文 Markdown：

```markdown
# [姓名] 周报（[起始日期]—[结束日期]）

## 本周概览

[3—5 句书面语，概括本周主线、覆盖范围和关键交付结果。不罗列代码模块名，不讲开发过程故事。]

## 工作内容

### 1. [新增 / 调整 / 补齐 / 修复 + 交付对象]

[2—4 句书面语：补充标题未写出的已验证主因、核心机制或关键能力，以及直接业务结果。附带特征写在正文。]

[如有未完成验收或遗留事项，用 1 句书面语附在本条末尾；没有则省略。]

### 2. [新增 / 调整 / 补齐 / 修复 + 交付对象]

[同上]
```

默认展示规范：
- 不附 commit hash、完整提交清单、逐文件列表、函数名或内部类型名（用户主动要求除外）；
- 不在每条工作项上重复写具体日期；
- 不强行给每条标提交数；仅当用户询问提交数量或存在明显统计口径差异时，在文末附一段简短的「统计口径说明」（说明主口径采用 author date 还是 committer date，以及 `--all`、stash、重复补丁造成的差异）。

## 交付前核对

1. 标题日期与用户指定范围一致；未指定时确认为「上周日到今天」，没有把结束日回退到上一个周日。
2. 作者身份与日期口径清晰准确，没有漏掉重要分支，也没有把 stash 或重复补丁算作独立交付。
3. 每条对应一个独立交付；若因文风反馈修改，条目集合与数量未被擅自合并或删减。
4. 逐句过四道检查：无注释话（无内部符号名、无模块堆砌）、无口语流水账、无盖住标题就空转的复述句、无性状化或分号拼接标题。
5. 未完成验证与遗留问题留在对应条目内，无单独的「风险与后续」和空洞收尾段。
6. 不了解仓库内部代码的管理者读完即可理解交付价值，可直接粘贴提交。
